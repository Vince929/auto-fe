# 前端考古文档精简指南

> fe-archaeology 专属精简指南，确保生成的文档精炼高效、项目特有。

---

## 核心原则

> **通用 = 删除 ｜ 项目特有 = 保留**

- ❌ 删除："React Hooks 是 React 16.8 引入的特性..." → 通用背景知识
- ✅ 保留："项目使用 `useProductDetail` Hook 封装商品详情加载逻辑（`src/pages/detail/hooks/`）" → 项目特有

- ❌ 删除："Redux 采用单向数据流..." → 通用理论
- ✅ 保留："`cartSlice` 管理购物车状态，主要 action：`addItem/removeItem/fetchCart`（`src/store/cart-slice.ts`）" → 项目特有

## 精简策略（按优先级）

### 第 1 优先级：立即删除（节省 30-50 行）

以下内容**无论如何都要删除**：

- ❌ **通用背景知识**：框架介绍、设计模式理论、最佳实践理论

  - ❌ "React 是 Facebook 开发的 UI 框架..."
  - ❌ "Redux 的核心思想是单向数据流..."
  - ❌ "组件化开发可以提高代码复用性..."

- ❌ **通用 API 使用介绍**：详细介绍 useState/useEffect 等通用 API 的工作原理

  - ❌ "useEffect 会在每次渲染后执行..."（通用知识）
  - ✅ "项目中 useEffect 必须声明依赖数组，ESLint 规则 exhaustive-deps 已启用" （项目规范）

- ❌ **冗长示例**：与项目代码无关的通用示例代码
  - ❌ "一个典型的 React 组件如下..." + 通用 HelloWorld 示例
  - ✅ 基于 `src/pages/xxx/index.tsx` 实际代码提炼的示例

### 第 2 优先级：有选择删除（节省 20-30 行）

根据项目实际情况删除：

- 项目**未使用**的状态管理特性（如项目用 Zustand 就删 Redux 相关内容）
- 项目**无后端直连**时删 GraphQL 相关内容
- 项目**无 SSR** 时删服务端渲染相关内容
- 项目**无单元测试**时删测试相关规范
- 项目**无微前端**时删微前端架构说明

### 第 3 优先级：合并与格式优化（节省 10-20 行）

- **把散文改成表格**（信息密度提升 50%）：

  ```markdown
  ❌ 不好的做法：
  项目使用 pnpm 作为包管理器，版本要求 8 以上。
  Node.js 版本要求 18 以上。使用 Vite 作为构建工具，配置文件在 vite.config.ts。

  ✅ 好的做法：
  | 工具 | 版本要求 | 配置文件 |
  |------|---------|---------|
  | Node.js | >=18 | — |
  | pnpm | >=8 | — |
  | Vite | ^5.0 | vite.config.ts |
  ```

- **把列表合并**：多个相关的单行内容合并为一个表格行
- **删除"待确认"项**：不确定的信息标记为"待确认"后不要放进最终文档
- **每个主题最多 1 个代码示例**：且必须是项目实际代码，不是通用示例

## .catpaw/rules 精简专项策略

> rules 层是 AI 自动加载的，`project-context.md` 直接包含完整项目背景+技术栈+规范+文档索引，AI 无需再跳转读取其他文件。

### project-context.md

**必须包含**：

- YAML frontmatter（`ruleType: Always` + `description` 一行摘要）
- 项目背景表（项目名/描述/目标平台/架构类型/业务领域）
- 技术栈表（框架/构建/状态管理/路由/HTTP/包管理）
- 框架关键特性（项目实际用到的特有特性，通用知识不写）
- 目录结构（2层深度 + 一句话注释）
- 快速启动命令
- 核心规范（命名/API/组件复用等）
- 文档索引表（指向 docs/ 各专题文档）
- docs 维护规则（代码变更 → 对应文档回写）

**禁止包含**：

- 通用框架介绍、设计模式理论、最佳实践解释
- 任何与项目无关的通用示例代码

## 精简前后对比示例

### 例子 1：状态切片说明

**❌ 不好（20行，大量通用内容）**：

```markdown
## cartSlice

购物车是电商系统的核心功能之一，用于临时存储用户选择的商品...（5行背景）

### State 结构

购物车 state 包含以下字段：

- items：商品列表数组
- totalPrice：计算得出的总价
- loading：加载状态，用于控制 loading 展示...（每项5行解释）

### 使用方式

使用 useSelector 从 store 获取购物车状态：
useSelector 是 React Redux 提供的 Hook，用于...（10行通用说明）
```

**✅ 好（8行，100%项目特有）**：

```markdown
### cartSlice — 购物车状态

- **路径**：`src/store/cart-slice.ts`
- **State**：`{ items: CartItem[]; totalPrice: number; loading: boolean }`
- **主要 actions**：`addItem(item)` / `removeItem(id)` / `fetchCart()（异步）`
- **选择器**：`selectCartItems(state)` / `selectTotalPrice(state)`
```

### 例子 2：API 通讯规范

**❌ 不好（15行，通用理论）**：

```markdown
## 通讯规范

在现代前端开发中，将 API 调用集中管理是最佳实践。
这样可以提高代码复用性，便于统一处理错误和 loading 状态...
（10行为什么这样做的解释）

✅ 应该在 store 的 thunk 中调用 API
❌ 不应该在组件中直接调用 API
```

**✅ 好（6行，直接规范）**：

```markdown
## 通讯规范

✅ MUST：所有请求在 `src/api/[domain].ts` 中封装，通过 `createAsyncThunk` 调用
❌ 严禁：在 React 组件内直接调用 `axios.get()` / `fetch()`
❌ 严禁：在组件内定义接口 URL 字符串
❌ 严禁：接口调用无 try/catch
```

## 快速减肥技巧

1. **把段落文字改成表格**：节省 50% 行数
2. **把分条列举改成单行**：`- 使用 RTK，禁止在组件中直接 dispatch axios` 而不是 5 行解释
3. **代码示例只保留关键部分**：省略 import/export，只保留核心逻辑
4. **路径引用代替描述**：`（见 src/api/request.ts）` 代替三句话解释它在哪
5. **删除所有"通常来说"、"一般情况下"开头的句子**：这些都是通用知识
