name: auto-fe-quick
chineseName: 前端自动化 - 快速模式
description: 轻量化的前端快速开发模式，跳过需求文档、技术文档生成、学城上传、大象拉群等正式流程。用户直接描述改动意图，AI 注入项目上下文后分析并列出改动点，用户确认后立即开始写代码，完成后输出 Git/Talos/通知的后续命令供用户按需执行。适用于不需要走 SDD 流程的任意功能改动，包括 bug 修复、功能调整、文案样式修改等。
---

## 使用方式

| 触发词 | 示例 |
|--------|------|
| `"quick：<描述>"` | `"quick：把首页 Banner 改成新版 UI"` |
| `"快速模式：<描述>"` | `"快速模式：修复订单列表翻页后滚动条不重置的 bug"` |
| `"帮我快速做一下，<描述>"` | `"帮我快速做一下，把搜索框 placeholder 文案改一下"` |
| `/auto-fe-quick <描述>` | `/auto-fe-quick 新增一个分享按钮` |

> 📌 无需提前准备 `requirement/` 文件夹，直接在对话中描述即可。

---

### 🗒️ 输出执行计划（启动后第一步，不可跳过）

在做任何事情之前，先在对话中输出以下执行计划（直接文字输出，不加代码块）：

📋 执行计划：

  阶段 1：加载项目上下文
    Step 1：读取 project-context.md
    Step 2：读取 docs/required/ 所有必读文档
    Step 3：逐条判断按需文档触发条件，输出判断清单
    Step 4：读取所有命中的按需文档

  阶段 2：分析改动
    Step 1：深入阅读涉及改动的现有代码文件
    Step 2：分析改动点，输出改动点清单

  🔴 Review 门：等待用户确认

  阶段 3：写代码

  🔴 停下，输出后续命令菜单（Commit / Talos / 大象通知）

> ⛔ **必须严格按照上述顺序执行每一个步骤，不得跳过、不得合并、不得重排。**
>
> ⛔ **每进入一个新阶段或新步骤时，必须先在对话中输出一行声明，格式为：**
> - 进入阶段：`▶ 开始执行 阶段1：加载项目上下文`
> - 进入步骤：`  ▷ Step 1：读取 project-context.md`
> **禁止在未输出声明的情况下直接执行操作。**

输出完毕后，立即开始执行阶段 1。

---

### 阶段 1：加载项目上下文

检查 `.catpaw/rules/project-context.md` 是否存在：
- **不存在** → 跳过，直接进入阶段 2
- **存在** → 按以下三步加载：

**Step 1：读取 `project-context.md`**（必须）

**Step 2：读取 `docs/required/` 下所有文档**（必须）

`docs/required/` 是始终生成的必读文档目录，里面的文档每次都必须读取（通常包含 `conventions.md`、`commands.md` 等）。

**Step 3：逐条判断 `docs/on-demand/` 触发条件，输出判断清单**

读取 `project-context.md` 的「按需阅读文档」表，**必须对每一条文档逐一判断其触发条件**，不可整体跳过，不可合并为"其余都跳过"。

> ⚠️ **匹配判断不能只看「是否新增/修改」，还要看「是否使用/读取」**：改动中只要涉及某个模块的数据读取、调用或依赖（即使不新增也不修改该模块本身），对应文档也应触发读取。例如：从状态库读取数据 → 触发 state-management；调用已有工具函数 → 触发 utils；使用已有公共组件 → 触发 components。

判断完毕后，**立即在对话中输出完整清单**（每条单独占一行，条目之间必须有空行），格式如下：

📚 已加载项目上下文：

  ✅ project-context.md

  ✅ docs/required/conventions.md（始终）

  ✅ docs/required/commands.md（始终）

  --- 按需阅读文档逐条判断 ---

  ✅ docs/on-demand/[文档名]（命中：[触发条件]）

  ⏭️ docs/on-demand/[文档名]（跳过：[触发条件]，本次不涉及）

  ...（每条都要列出，不可省略）

> ⚠️ Step 3 只做判断和输出清单，**不读取任何文件**，读取在 Step 4 统一执行。

**Step 4：读取所有命中的按需文档**

遍历 Step 3 清单中所有标记为 `✅` 的 `docs/on-demand/` 条目，**逐一调用 read_file 读取**（可并行）。

> ⛔ **每一条 `✅` 条目都必须有对应的 read_file 调用，不得跳过任何一条。**

> ⚠️ 此阶段无 checkpoint，执行完直接进入阶段 2。

---

### 阶段 2：分析改动 → 列出改动点清单

#### Step 1：深入阅读涉及改动的现有代码

根据用户描述，**主动读取**可能涉及的现有代码文件（不依赖项目上下文文档的描述，直接用 read_file / grep 查找并读取）：

- 涉及的页面/组件文件
- 涉及的 store/slice 文件（如有状态变更）
- 涉及的工具函数/hooks（如有引用）
- 类型定义文件（如有类型改动）

> ⚠️ 读取目的是**了解改前状态**，确保改动点描述准确（尤其是 MODIFIED 类型的「改前状态」），同时发现用户描述中未提及的隐性关联。
> ⚠️ 如用户描述已足够清晰、改动范围极小，可跳过此步，但需在对话中说明跳过原因。

#### Step 2：分析改动，列出改动点清单

结合用户描述 + 项目上下文 + Step 1 读取的代码，以**前端视角**分析本次改动。**分析过程中**遇到以下情况，**立即暂停询问，等用户回复后再继续分析**（不先输出清单）：

- 需求描述模糊，改动范围有歧义
- MODIFIED 类改动不清楚「改前状态」是什么
- 不确定涉及哪个页面/组件/功能
- 存在多种合理理解，需要用户确认意图

**澄清完毕后**，在对话中直接输出以下内容（不加代码块，直接作为回复文字输出，不生成任何文件）：

#### 改动点清单格式

## 📋 改动点清单

**需求描述：** <一句话总结用户意图>

### 改动点
| # | 类型 | 文件（预估） | 描述 |
|---|------|------------|------|
| 1 | MODIFIED | src/pages/Home/Banner.tsx | 将旧版 Banner 替换为新版 UI 组件 |
| 2 | MODIFIED | src/pages/Home/index.module.scss | 调整对应样式变量 |
| 3 | ADDED | src/components/BannerV2/index.tsx | 新增 BannerV2 组件 |

> ⚠️ 涉及文件列表仅为预估，实际修改范围请以代码实现为准。

**规则：**
- MODIFIED：必须说明「改前状态」和「改后状态」；不清楚改前时**立即暂停询问**，等用户回复后再继续，不猜测、不跳过
- REMOVED：必须描述清理范围（文件、路由、import 引用逐条列出）
- 改动点之间如有依赖关系，需标注先后顺序

---

### 🔴 Review 门：等待用户确认

输出改动点清单后，**必须停下等待用户明确确认**，禁止自动进入阶段 3。

提示用户：
> "请确认以上改动点是否正确？有需要补充或修改的地方请告知，确认后我将开始写代码。"

用户回复"没问题"/"确认"/"开始"等 → 进入阶段 3。

---

### 阶段 3：写代码

#### 3.1 确认当前分支

读取当前分支名：`git rev-parse --abbrev-ref HEAD`，告知用户将在当前分支上直接操作，**不新建分支**。

#### 3.2 按改动点逐项实现

主 agent 直接逐项实现代码，**不 spawn sub-agent**：

- 按改动点清单顺序依次执行，有依赖关系的改动点保持先后顺序
- 遇到信息不足时，优先结合用户原始描述和项目上下文自行判断，判断不了则立即暂停询问用户，等用户回复后继续
- **写代码阶段只修改文件，不执行任何 commit**
- 所有改动点完成后进入停止点

---

### 🔴 停下，输出后续命令菜单

代码写完后，**停下，不自动 commit/推送/发布/通知**，直接输出以下内容（不加代码块，直接作为回复文字输出）：

> ⛔ **必须完整输出以下所有模块（Commit、Talos、大象通知），不得删减任何一个，不得合并，每个模块之间保留一个空行。**

✅ 代码修改完成！

接下来可以执行以下操作（均为可选，按需触发）：

📝 Commit & 推送（当前分支：<branchName>）

已准备好提交和推送，输入确认后我立即执行：

  → git add -A
    git commit -m "feat/fix/...: <中文简述>"
    git push origin <branchName>

💡 如需修改 commit message，告诉我你想要的描述即可。

🚀 Talos 发布（可选）

告诉我"帮我发布"，并提供以下信息：
  • Talos 发布页面 URL（打开 Talos 复制地址栏链接即可）
  • 你的 MIS 账号（用于 Talos operator）

我会自动提取 appId / templateId、查询发布环境并触发发布，持续等待结果。

📢 大象通知（可选）

告诉我"帮我通知"，并提供以下信息：
  • 验收群成员 MIS 列表（测试人员、产品经理等，如：["zhangsan", "lisi"]）
  • 测试环境 URL（需要你自己填写，AI 无法自动获取）

我会建验收群并发送部署通知。

---

### 后续操作：提交 & 推送

用户确认后执行：

1. **推断 commit message**：根据本次改动点清单，自动生成一条 `feat/fix/refactor/style: <中文简述>` 格式的描述；若用户已明确告知 message，使用用户提供的。
2. **直接执行以下命令**，完成后告知推送结果：
   ```
   git add -A
   git commit -m "<自动生成的 message>"
   git push origin <branchName>
   ```

---

### 后续操作：发布

用户说"帮我发布"并提供配置后，spawn `auto-fe-talos` sub-agent 执行：

从 Talos 发布页面 URL 中提取 `appId` 和 `templateId`（URL 格式：`https://talos-better.sankuai.com/release?appId=<appId>&...&templateId=<templateId>`）。

spawn sub-agent 的 prompt 包含：
```
talos 配置:
  appId: <从用户提供的 URL 提取>     ← 来源：聊天窗口
  templateId: <从用户提供的 URL 提取> ← 来源：聊天窗口
  （target 由 sub-agent 自动查询获取，无需传入）
branchName: <当前分支名>             ← 来源：git rev-parse --abbrev-ref HEAD
operator (myMis): <优先从用户记忆读取，无记录则询问用户> ← 读取步骤见下文
```

> ❌ **绝对不读取任何配置文件中的 MIS。**
>
> **`operator / myMis` 读取步骤：**
> 1. 读取 `.catpaw/rules/memory-user-index.md`，查找包含 MIS / mis / 账号 的条目
> 2. 若有，读取对应主题文件获取 MIS 值
> 3. 若无记录，询问用户：「请告诉我你的 MIS 账号（用于 Talos operator）」，等用户回复后再继续，不得跳过、不得猜测

sub-agent 触发发布并持续轮询，返回成功/失败结果后：
- **成功** → 输出测试链接，提示可以进行验收
- **失败** → 输出错误日志和构建链接，**暂停等待用户处理**

---

### 后续操作：通知

用户说"帮我通知"后，调用 `/auto-fe-notify` 工具完成：

**拉群**（告知群成员 MIS 即可，用户自身 MIS 从 `.catpaw/rules/memory-user-index.md` 自动读取）：
```
帮我拉个群，成员：<mis1>、<mis2>，群名「<需求简称>-前端」
```

**发消息**（已有群时，提供 groupId）：
```
帮我发消息到群 <groupId>，内容：前端已发布测试环境，请开始验收 🙏，@<mis1> @<mis2>
```

> 💡 详细使用方式参考 `cmds/auto-fe-notify/SKILL.md`

---

## ⚠️ 重要原则

- **不生成任何产物文件**（无 tec-doc.md / analysis.json / tasks.md 等）
- **不依赖 requirement/ 文件夹**，一切配置通过对话或用户记忆（`.catpaw/rules/memory-user-index.md`）收集
- **改动点 Review 门强制暂停**，用户确认前禁止写代码
- **停止点强制暂停**，用户主动触发才执行推送/发布/通知
- 遇到任何不确定的地方，**必须暂停询问**，不猜测、不跳过
